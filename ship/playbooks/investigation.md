# Investigation

You own the answer. This playbook is read-only: no edits, commits, or PRs.

1. Trace how it works, from entry point to effect, by reading the code instead of guessing. Fan broad searches out to subagents.
2. For "why" questions, read the history: git log and blame on the lines that matter, the PRs and tickets they link, and design docs in the repo.
3. Write the answer in this shape: Overview, Key concepts, How it works, Where things live (`file:line`), Gotchas. For a choice between options, give a recommendation with a tradeoffs table instead.
4. Apply the unslop skill to the reply.

If the answer shows that code should change, stop and say so. The user decides whether to run Bug or Feature next.

**Reply:** the answer, with every claim cited to code, history, or a run, or labelled as a guess. For "are we sure?" questions, give your real judgment and push back when the premise is wrong. Show flows visually when the harness can render them.

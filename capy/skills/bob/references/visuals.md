# Visuals in Capy

Use a diagram, file map, comparison, screenshot, or status table when it explains the result faster than prose. Tie each claim to code, history, or a real run. Keep paths and links usable from the recipient's machine.

For HTML explanations, read Capy's installed `make-a-page` skill and its artifact frame guidance. Build a self-contained file with inline styles, scripts, SVG, and images. The viewer blocks external requests, so do not load a CDN diagram library or web fonts. Verify with the installed frame harness and inspect the output before handing it back. Do not install a browser merely to render a reply.

Follow the native `artifact` skill's output rules. An ordinary plan or answer does not automatically authorize publishing or creating a share link. Use the supplied project Drive path for files that need to survive a machine change. A subagent attaches evidence to its parent report using the available native controls.

If those rendering skills or tools are unavailable, use Markdown tables and Mermaid or an inline SVG file, label that limitation, and continue. A missing renderer must not block an investigation answer.

Show the playbook plan with checkpoints; changes as a file map with ownership and connections; design choices side by side with the recommendation; investigations as a flow with source locations or a decision timeline with confidence; PR readiness as a check/review/gate table. Include before/after screenshots when they prove user-visible behavior. Avoid decorative dashboards that add no evidence.

PR bodies use a text file tree and ordinary image links that a GitHub reviewer can open. Local absolute paths alone are not shared evidence.

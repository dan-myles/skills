# Create

Write `bob-verify-<app>` for this repo and prove it works before handing it over.

1. **Read the repo.** Answer these from the code, the README, and the scripts. Ask the user only what you can't observe.
   - **Surface.** What a user touches: a web UI, a CLI or TUI, a desktop or mobile app, an API, a library. Pick the main one and note the others.
   - **Run.** The repo's own dev command, plus ports, env vars, seed data, and auth.
   - **Drive.** How an agent can act on it from a shell. Use what the repo has first: Playwright or Cypress specs, expect scripts, a debug port, curl-able routes. Otherwise pick a plain recipe: a browser over CDP for web and Electron, tmux or a PTY for a CLI or TUI, HTTP for a service. Prefer commands any agent can run over one harness's built-in tools.
   - **Observe.** What evidence exists: screenshots, accessibility snapshots, terminal transcripts, response bodies, logs, exit codes, stored data.
   - **Isolate.** Whether two instances can run side by side (ports, data dirs, profiles). Parallel threads and worktrees are common, so plan for it. If they can't, the skill says so and refuses to drive an instance it didn't start.
2. **Get it running.** If the checkout doesn't build or start, fix that or report exactly what's broken before writing anything. A skill written against a broken app teaches wrong steps. If a missing asset the feature doesn't need blocks startup, the skill may create it, marked as verification scaffolding, and remove it in cleanup.
3. **Write `SKILL.md`.** Frontmatter: `name: bob-verify-<app>` and a `description` naming the app, the surface, and when to use it ("prove a change to <app>'s UI or CLI works"). Then these sections, every one filled from what step 1 found, with no placeholders:
   - **Launch.** The exact command, how to tell it's ready, and how to stop it. Launch reaches a usable state from an empty data dir, migrations and seed data included, and ready means usable: a port that answers or a database health check can pass while init is still running. Wait for the signal that comes after setup finishes (a log line, a prompt, a query that returns seed data). For a short-lived CLI, launch means build once, then each drive gets its own fresh PTY or tmux session.
   - **Doctor.** One read-only check that this instance is worth driving: the process is up, it's the right build, the port is ours, auth works. Run it first, and again whenever something looks off.
   - **Drive.** The recipe with this repo's real handles: accessible names and roles, data attributes, prompt strings, routes. Never coordinates or tab order.
   - **Evidence.** What to capture and where it goes. Drive the real user path, not internal setters or test-only routes. Capture the action and the resulting state. Check side effects (files written, rows stored, messages sent) along with the screen. Mock only where production already isolates an external system. When the safe path is a dry run, watch what it actually skips (files, network, git refs) instead of trusting its name.
   - **Cleanup.** Stop what the run started and clear scratch state. Keep the evidence.
   - **Helpers.** Any script the skill ships is executable, and the skill shows how to call it.
4. **Seed the feature map.** `features/README.md` plus one file per user-facing feature, starting with the top three to five (from routes, commands, menus, docs). Follow `references/feature-map-example/`. The README holds baseline preconditions, driving conventions, proof rules, and the index. Each feature file has a title, one paragraph of what the user sees, then four sections in order: `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, and `Gotchas`. List every entry point a user has; a proof through one convenient path doesn't cover the others. If the seed data can't meet a journey's preconditions, the journey reports a failure and the reason goes in that feature's `Gotchas`. Never weaken a journey so it passes.
5. **Place it.** Save the skill at `.agents/skills/bob-verify-<app>/`, with lowercase-hyphen folder name, matching `name`, and a nonempty `description`. Keep one canonical copy. Repo skills load from the starting branch on cloud machines, or from disk on local machines.
6. **Prove it.** Follow the new skill end to end, as written: launch, doctor, drive one mapped feature, capture evidence, clean up. Then check the evidence is still there. Fix whatever failed, and run cleanup after every failed try so nothing is left running. A skill that was never run is a draft. If you proved it in a stand-in for the real target (a container instead of a fresh VM, a local stack instead of a remote one), list every setup step the stand-in did that the target won't. Those stay unverified until a run on the real target covers them.
7. **Ship it.** Commit on a branch and open a PR per the repo's AGENTS.md. It's a new file set and nothing else.

**Reply:** the surface and harness you chose and why, the features mapped, the proof run's evidence paths, what you couldn't reach and why, the PR link, and a pointer to `/bob-verify maintain` for when the app changes. **Show:** the feature map with what the proof run covered.

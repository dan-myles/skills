# Bug

The fix is yours. Work from evidence: each line you ship should answer something you saw happen at runtime. Changes made on a hunch are experiments, and experiments don't ship. If a test of an idea comes back negative, undo the edits that idea led to.

1. See it fail yourself, on the surface where it was reported. Drive the browser, simulator, API, or CLI through the repo's verify skill when it has one, otherwise with the harness's tools, and save the failing output. Show it: the screenshot or output, inline. Ask the user to reproduce it only when nothing you have can reach that surface, and explain the gap. When it won't fail on demand, build the trigger yourself, narrow the conditions, or add logging until it does.
2. Narrow down the cause. Write out what could cause it. Run `cooper-how` over the affected area to ground the list. When it looks like a regression, run `cooper-why` on the code that broke to find what changed and what that change was for. Each round, run the check that rules out the most suspects at once, using real output from logs, added instrumentation, or a debugger. When you can show how the failure happens, you've found it. Show the suspects as a tree as you go, ruled-out ones struck through with the check that ruled them out. Follow `fix-root-causes`, and switch to `attack-the-premise` when two fixes on the same assumption have failed.
3. Plan the smallest fix that matches what you found. When the fix changes the schema, infrastructure, or another call that's the user's (see **When** in `../cooper-grill/SKILL.md`), that's a **Checkpoint**: run `cooper-grill` on it first. When only the right behavior is unclear, pick the one the code, tests, and docs point to and name it in the PR. If it reaches across modules, run `cooper-architect` and build against its sketch; changing a public interface is a contract, so it grills first. When the fix touches code other modules depend on, run `cooper-blast-radius` on the planned edit and put its risks in the brief. When the fix touches more than one file, show a file map per **File maps** in `references/visuals.md` of the plan.
4. Write the regression test and watch it fail, then commit it. Write one when the bug sits in business logic and a local test is cheap; calling `/cooper` on a bug is the user's request for that test. Use the repo's test conventions and assert on behavior, not plumbing, per `test-behavior-not-implementation`. Mark it `skip: <why>` when the test would be slow, need heavy integration setup, or have no clear shape, and commit the step 1 reproduction script instead when there is one.
5. Build the fix, verifying it as a piece. Hand it to a subagent with a clear scope and the check that proves it: the step 4 test going green, or the reproduction command. The subagent runs the check and reports its output. Rerun it yourself, then commit the fix on top of the test.
6. Review per **Review** in the skill. It comes before the final check because its fixes change code.
7. Verify on the final code: run the step 1 reproduction again on the same surface and show that it passes now, as a **Proof gallery** per `references/visuals.md`: the failure from step 1 next to the pass. Passing unit tests cover the branches they hit; they don't show the bug is gone. Run the repo's checks. Any code change after this, including a Babysit fix, reruns this check for what it touched before it's pushed.
8. Ship it: run `playbooks/open-pr.md`, which opens a ready-for-review PR and babysits it. Stop when Open PR stops.

**Reply:** what went wrong, the cause and the evidence for it, the fix, how you checked it, the reproduction output from before and after copied exactly, and the branch it's committed on. **Show:** the failure path with the point it broke, the reproduction before and after, and the file map of what changed.

**End-of-work reply:** follow the [required recap](../references/visuals.md#required-end-of-work-recap): the diagram and the built-work recap first, then concise caveats and handoff links. This also applies when this playbook ends in a PR or babysit handoff.

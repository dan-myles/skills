# Feature

The design is yours. Hand off the typing, keep the decisions.

1. Learn the ground first. Run `cooper-how` over the area the change touches: its code paths, data shapes, and module boundaries. Read what the repo's rules say about that area. When the design would rework code that looks deliberate, run `cooper-why` on it too and carry its Keep/Change/Avoid/Risk into the draft. Show what you learned as a file map per **File maps** in `references/visuals.md`: the area's existing files and how they connect, before drafting.
2. **Checkpoint** when the feature changes the schema, infrastructure, or another call that's the user's and the request doesn't settle it (see **When** in `../cooper-grill/SKILL.md`): run `cooper-grill` before drafting, and design from the decisions it saves. Otherwise mark this `skip: <why>` and decide the rest yourself.
3. Draft the design: the data shape and its structure, where it lives, its public signatures, and how current code will call it, per `model-the-domain` and `foundational-thinking`. When it lands in an existing design, also `redesign-from-first-principles`. When the change adds a service, a module, or a public interface, or moves ownership between modules, run `cooper-architect` for the draft. Otherwise draft it yourself. Show the draft with a file map of where every new and changed file goes, and keep going: the design is yours. When drafting turns up a call that's the user's and step 2 didn't settle (a product or taste call the request and the code don't settle, a one-way door, a reserved call), that's a **Checkpoint**: run `cooper-grill` on it with the draft in hand, two directions when both are reasonable, and your pick. Nothing else stops here, however sensitive the area; Review's decision check and `cooper-blast-radius` cover the rest.
4. Plan the work as four todo items. Keep an item that doesn't apply, marked `n/a: <why>`.
   - **Goes first.** Anything the rest depends on: schemas, API specs, shared types, generated code.
   - **Runs in parallel.** Pieces in separate files, services, or layers.
   - **Contended.** Files or resources more than one worker would edit. Split them up, or do them one at a time.
   - **Worker count.** How many workers, and the reason.
5. Build it, verifying each piece. Brief subagents from the plan with files, data shape, what done looks like, and the check that proves the piece works: a test, a command, a request. The subagent runs that check and reports its output. Rerun it yourself before you commit the piece, and don't start work that builds on a piece until its check passes (`sequence-verifiable-units`). Finish the "goes first" work, then run the parallel pieces together. Repetitive edits get a script, per `build-the-lever`. A `cooper-architect` sketch is the contract: follow its **Building against the sketch** and **Scrapping it** sections.
6. Review per **Review** in the skill. It comes before the final check because its fixes change code.
7. Verify it all together on the final code, and show it as a **Proof gallery** per `references/visuals.md`. Check it where the user will meet it: the page, the screen, the endpoint, the command, through the repo's verify skill when it has one. Run the repo's checks. A check that's unclear or on the wrong surface hasn't passed. Report it that way. Any code change after this, including a Babysit fix, reruns this check for what it touched before it's pushed.
8. Ship it: run `playbooks/open-pr.md`, which opens a ready-for-review PR and babysits it. Stop when Open PR stops.

**Reply:** what you built and for whom, the choices you made and why (a table when you weighed options), the evidence that it works, the branch it's committed on, and anything still undecided. **Show:** the file map of what changed, badged, plus a table when you weighed options.

**End-of-work reply:** follow the [required recap](../references/visuals.md#required-end-of-work-recap): the diagram and the built-work recap first, then concise caveats and handoff links. This also applies when this playbook ends in a PR or babysit handoff.
